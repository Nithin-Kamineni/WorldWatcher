Progress report against issues.txt - Play panel redesign
(written per issues.txt point 11)

Legend: [x] done  [~] partially done (see note)  [ ] not done

=====================================================================
1. STARTING PLAY PANEL
=====================================================================
[x] 1.1 Single clean page to choose session + chat, few clicks.
    Rebuilt SessionRunnerSetupScreen.tsx as one page, two columns
    ("Session prep" / "Notes thread") side by side, one "Start running"
    button. Accepting the defaults is a single click.

[x] 1.2 Default session = most recent; default chat = most recent;
    option to not pick a chat at all.
    Both columns auto-select their most-recently-updated item on load.
    Added a third "No notes thread" card (in addition to the existing
    "Start a fresh thread" card and the list of existing chats) that
    lets the DM skip DM notes for the session entirely.

=====================================================================
2. MAIN PLAY PANEL PAGE
=====================================================================
[x] 1. Breadcrumbs removed from the Play page entirely (PlayPage.tsx
    no longer renders <Breadcrumbs>).

[x] 2/3. Multiple, heavily-editable layouts. Implemented a generic
    recursive split-pane engine (SplitPane.tsx) over 6 static layout
    trees (playLayoutTrees.ts) matching the spec exactly:
      1. single window
      2. double, side by side
      3. double, stacked
      4. triple, evenly split
      5. triple, one half + two quarters
      6. quad, one per corner
    One component renders all 6 - no per-layout special-casing.

[x] 4/5. Layout switcher: a toolbar (PlayLayoutToolbar.tsx) sits at
    the top of the Play workspace with 2 quick-access layout icons
    plus a "More layouts" popover for the other 4.
    NOTE: this toolbar is a page-level bar at the top of the Play
    page's own content area, not an injection into the app's global
    TopBar component. TopBar is shared by every page in the app and
    has no per-page action-slot mechanism today (confirmed by reading
    it) - adding Play-specific layout icons directly into the global
    navbar would show them on every other page too. Functionally this
    reads as "the navbar for the Play page" (persistent top bar, same
    row as the back button), which is what the spec is asking for in
    practice, but it is a real MUI Toolbar the Play page owns, not a
    modification of the shared TopBar. Flagging the interpretation
    since it wasn't explicitly asked for in this form.
    Which 2 layouts are "quick access" was my judgment call (spec
    didn't say which two): picked Double/side-by-side (the default)
    and Triple/evenly-split as the most complete common setup. Easy
    to change (QUICK_LAYOUT_IDS in playLayoutTrees.ts) if a different
    pair is wanted.

[x] 6.1. Removed the game-controller icon, the session title, the
    "Running now" caption, and the "Change session" button entirely
    from the workspace header.

[x] 6.2. A dedicated back button on the toolbar (left side) returns
    from the workspace to the setup screen.

[x] 7. Lock toggle next to the layout buttons - when locked, both the
    layout-switch buttons and the resize dividers are disabled, so
    nothing about the arrangement can change accidentally mid-session.

[x] 8. Resizing:
    8.1/8.2/8.3 - every layout's dividers are draggable (generic to
    all 6 via SplitPane), including the side-by-side drag-left/right
    behavior and the triple-half layout's two independent dividers
    (left/right split, and the top/bottom split within the right
    half).
    8.4 - DM Notes/chat panes have a single-click collapse button;
    collapse direction (horizontal strip vs vertical strip) is
    inferred automatically from whether the pane sits in a row-split
    or column-split, matching "depending on the layout" in the spec.
    8.5 - sizes and collapsed state persist per campaign (localStorage
    via usePlayLayoutStore, same pattern as the rest of this codebase's
    UI-preference stores). "Reset layout" button clears the current
    layout's remembered sizes back to an even split.

[x] 9. Default layout is double/side-by-side.

[x] 10.1. Any window's content can be changed via an icon button in
    its own header (WindowKindSwitcher) - the current kind's icon
    doubles as the button, opening a menu of the other 2 kinds.

[~] 10.2. Posh/elegant visuals - structurally complete (rounded
    Paper cards, consistent header treatment across all window types,
    matching the existing app's MUI theme) but a dedicated visual-
    polish pass against the reference screenshots wasn't done as a
    separate step - the components were styled to match the existing
    codebase's conventions (BBCodeEditor, FilterChipGroup, etc.)
    rather than pixel-matching the uploaded images.

[x] 10.3.a Session window: read-only render of the note (existing,
    kept) plus a new "Quick edit" header button that swaps in the
    real BBCodeEditor in place, saving on toggle-off - no navigation
    away from Play needed for small touch-ups.

[x] 10.3.b DM notes chat: header menu to switch/create chats (existing,
    kept). Added: when no chat is selected, the panel renders blurred
    with "Choose a chat" / "Start a new chat" buttons instead of an
    empty message list.
[~] 10.3.b.3 "Chats saved in the folders section in the session
    folder, viewable/editable there" - implemented as an "Attached
    chats" section directly on the session-prep note's own page
    (NoteDetailPage.tsx), with inline rename and a "Run" shortcut
    into Play. NOT implemented as literal sibling rows inside
    NotesFolderExplorer's own grid/table folder browser - that
    component's rendering is driven purely by Note/NoteFolder arrays
    today, and teaching it to also render SessionChat rows (which
    have no folderId of their own, only a noteId) touches a larger
    shared component used across all of Notes. Scoped out of this
    pass; the chats are visible and editable, just one click away
    from the folder view (on the session note itself) rather than
    inline in the folder listing.

[x] 10.3.c Items window: Chrome-tab strip, closable via the x on each
    tab, a "+" menu to reopen a closed sub-window kind. Random Tables
    opens by default.

[x] 10.3.c.3 Random Tables sub-window, theme-based:
    [x] 3a. One-row search + filter icon opening a popover; each
        filter group with more than 8 options gets its own search box
        to narrow the option list (built to scale as more themes/
        tables are added later).
    [x] 3b. Pinning - a pinned table is never replaced; a new pick
        from search fills the one "current" (unpinned) slot below the
        pinned ones.
    [x] 3c. Pins persist across reload/logoff (localStorage).
    [x] 3d. Search + filter share one row.
    [x] 3e. Every table starts collapsed, showing a tagline (theme +
        column count).
    [x] 3f. Uncollapsing shows the full roll table (same roll-per-
        column / roll-all mechanic as the original panel).

[x] 10.3.c.4 Encounters sub-window: same search/filter/pin/collapse
    shell, tagline shows CR + creature count + theme.
    [x] 4a. Same pin/collapse mechanism.
    [~] 4b. Expanded view shows the full creature roster for a fixed
        encounter, or a short "resolves via random-table roll" note
        for a random-table encounter. The spec also asks for
        something shown "if the encounter is social or exploration" -
        the Encounter data model in this codebase doesn't currently
        distinguish social/exploration content beyond a free-text
        `encounterType`/`description`, so there's no structured data
        to build a distinct view from yet; this is a data-model gap,
        not a UI gap, and adding it wasn't in scope here.
    [x] 4c. New compact UI built specifically for this space (not
        reused from the full Encounters page).

[x] 10.3.c.5 Stats sub-window: All/Creature/Spell/Magic-Item toggle
    (default All) above the shared search bar, using each entity's
    existing server-side "browse" endpoint. Same pin/collapse shell.

[x] 10.3.c.6 Places sub-window: countries/settlements/buildings/
    dungeons, filtered out of the world's Article catalog by the
    existing "Places" article group. New compact summary UI (shows up
    to 4 key fields + a body snippet) sized for the sub-window.

[~] 10.3.c.7 "Open in new tab" on every item:
    [x] Places - opens the article's real per-entity route
        (/w/:worldId/manager/entry/:id) - works exactly as asked.
    [x] Random Tables - opens the full Situational Tables reference
        page and scrolls to / outlines the specific table (added
        `?table=` support to SituationalTablesView for this).
    [~] Encounters - opens the Encounters page's management view, but
        doesn't scroll to / highlight the specific encounter.
    [~] Stats (creature/spell/item) - opens the Compendium page, but
        doesn't deep-link to the specific entry.
    The last two open the right page rather than the specific item,
    to avoid expanding this already-large pass into rebuilding those
    two pages' own query-param/deep-link handling from scratch.

[x] 10.3.c.8 Default arrangement left-to-right: Session, Items
    (Random Tables active), Chat - matches exactly for every layout
    that has 3+ panes; the 2-pane layouts show Session + Items (no
    room for a 3rd default pane); quad's 4th pane defaults to a
    second, independent Items window (spec didn't specify a default
    for a 4th pane).

NOT ATTEMPTED / OUT OF SCOPE THIS PASS

  Client-only (new Zustand stores, all localStorage-persisted UI
  state), consistent with issues.txt not asking for schema changes.

  visual pass (10.2) - the new components follow this codebase's

  NotesFolderExplorer's own folder browser (10.3.b.3).

  item (10.3.c.7).

  distinct data to render from yet (data-model gap).
