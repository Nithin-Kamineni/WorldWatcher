--- B0. ORIGINAL FRAMING --------------------------------------------

The Encounters page used to hold four overlapping sections - random
encounters, encounter management, roleplay and exploration - where
"encounter management" and "random encounters" did more or less the same
thing. The whole thing was to be restructured: a RANDOM TABLE is the
rollable container, and ENCOUNTERS are the items inside it (the old
model had it backwards, with random tables holding multiple encounters).
Existing data had to be migrated afterwards into the new structure with
correct formats, correct placement and reasonable tags. The roleplay and
exploration sections were rehauled by the same changes.

STACK CONTEXT (respect what exists - never rebuild or duplicate it):
React + Konva + Vite + TypeScript + Zustand frontend; FastAPI +
PostgreSQL backend. The app already has creature/monster stat blocks,
spells and magic items (D&D Beyond + 5e SRD, with CR/HP/type), an
initiative + combat tracker (HP/conditions), a faction relationship
graph, an NPC generator and NPC records, a quest tracker, and maps with
fog of war. Combat encounters must LINK to existing creature stat-block
rows, social encounters to existing NPC rows, treasure tables to
existing magic-item rows - storing only encounter-specific metadata
(quantity, role, attitude) on the join rows, so a stat-block edit
propagates everywhere.

CORE DESIGN PHILOSOPHY - a random table is described along THREE
INDEPENDENT dimensions, kept as three separate fields, never collapsed:
  1. CATEGORY - what the table is ABOUT. Exactly ONE per table. A node
     in a browsable tree.
  2. TAGS - cross-cutting facets for search/filter (environment, tier,
     theme, source book). MANY per table.
  3. FORMAT - how the table is STRUCTURED and rolled. Exactly ONE.
Example: a forest tier-1 wandering-monster table has
category = Encounters > Combat, tags = [env:forest, tier:1,
pillar:combat, phase:travel], format = lookup (or scene_generator).
Environment and tier are TAGS, never categories - category nodes per
environment or tier make the tree explode combinatorially.

PART I - UI REFINEMENT BACKLOG
#####################################################################
Deliberately sits next to Part E: both are live backlogs. Part E is the
tail of the two big feature efforts; this part is the UI-quality work
that came out of the 2026-09-03 Play-page refinement round - what that
round did NOT do, plus the same class of problem elsewhere in the app.

Context for the P-series. The Play page now has: pane-accurate layout
icons drawn from the layout trees themselves (LayoutGlyph.tsx), one
40px pane header everywhere (PaneHeader.tsx), closable panes that leave
a droppable empty placeholder (EmptyPaneWindow.tsx) or hand their space
back to their neighbours, header drag-and-drop pane swapping with a snap
tint (paneDrag.tsx / PaneDropZone.tsx), Items state keyed per pane slot
so two Items windows are independent, and usefulness-ranked random-table
search and browse (tableSearch.ts + useTableUsageStore.ts).

--- I-P. PLAY PAGE --------------------------------------------------

❌  P1  Pane drag-and-drop only SWAPS two panes. Dropping on a pane's
        edge to split it, or dropping to create a new row/column, is not
        supported - so the reachable arrangements are still the 6 static
        trees in playLayoutTrees.ts, minus whatever is closed. A DM who
        wants "three panes, the middle one narrow and split top/bottom"
        still cannot build it.

❌  P2  Pane rearranging is mouse-only. It uses native HTML5 drag, so
        there is no keyboard path to move or swap a window and no
        pointer-event fallback for touch. This is also why it cannot be
        driven by Playwright's real mouse (see E12).

❌  P3  A sub-tab can only be reordered within its own Items window.
        Dragging a sub-tab into the OTHER Items window, or tearing one
        off into its own pane, is not supported - which is the natural
        next thing to try once two Items windows exist.

❌  P4  Closing a pane leaves an empty placeholder, but nothing
        remembers what used to be in it. "Bring closed windows back"
        restores the SPACE, not the window kind that was there; the DM
        has to pick the kind again.

❌  P5  Still only three window kinds (Session Notes / DM Notes /
        Items). A 'map' kind and an 'initiative tracker' kind are what
        E13 actually needs, and are the obvious way to make Play the
        single command centre instead of one of three routes a DM keeps
        switching between mid-session.

❌  P7  Per-slot Items state is never garbage-collected. Pins, opened
        rows and expanded rows persist per pane slot in localStorage
        forever, including slots belonging to layouts the DM no longer
        uses, and there is no "clear this window" action. Reset clears
        the layout, not the Items state behind it.

❌  P8  Only Random Tables got usefulness ranking. Encounters, Stats,
        Places and Factions still sort alphabetically AND still refuse
        to list anything until something is typed - so a sub-window
        opened mid-fight starts empty. Each needs the same treatment: a
        usage signal recorded on open/use, and a ranked default list.

❌  P9  Usage signals (useTableUsageStore) are localStorage-only, so
        "most useful" resets on a new browser or machine and cannot
        inform anything server-side. Worth a real table on the server
        once the ranking has proven itself in play.

⚠️  P10 The Items tab strip does not handle overflow. Each tab caps at
        168px and shrinks to a 32px minimum, so five tabs in a narrow
        pane crush together with no scroll and no overflow menu.

⚠️  P11 Chat-pane collapse and pane close now overlap conceptually -
        collapse is a chat-only thin strip, close is generic and leaves
        an empty placeholder - and a chat pane carries both at once.
        Decide whether collapse becomes generic (any pane collapsible to
        a strip) or goes away in favour of close.

⚠️  P12 A truncated pane title has no tooltip, so a long session-note
        name cannot be read without widening the pane.

--- I-U. THE REST OF THE APPLICATION --------------------------------

❌  U1  Header/toolbar scale is not consistent app-wide. Play's panes
        are now a deliberate 40px; the section headers on the world,

❌  U2  Encounters page still browses encounters in its own view rather

❌  U3  The client ships as one 2.27 MB (675 kB gzipped) chunk with no

❌  F1.4  Undo/redo covers floor-level edits only (tokens, shapes, flip,
          rotate). Grid settings, initiative/roll state and
          encounter-lock changes are deliberately excluded - not typical
          "oops" targets, and they would flood the history stack.
❌  F1.5  Combat tracking is deliberately lightweight (HP, concentration,
          death saves, freeform notes) - no structured spell-slot or
          resource system, per the user's "don't bother too much, I will
          improve it later".
❌  F1.6  "Cancel" exists only in the pre-start "rolling" initiative
          state; once active, "End Encounter" is the one-click way out.
❌  F1.7  Custom one-off encounter creature entries carry a flat size
          rather than the default/current size split, since a one-off
          entry has no reusable definition to reset back to.

--- F2. NOTES, ARTICLES, WORLD MANAGER -------------------------------

❌  F2.1  Notes' "Plots" toggle and the World Manager's "Characters" item
          are both bare ComingSoon placeholders - relocated, never built.
          No requirement has asked for real functionality yet.
❌  F2.2  Note bodies use the same hand-rolled BBCode editor as Articles,
          with no interactive checkboxes - so the session-prep
          "checklist" is a styled list of prompts to fill in, not
          tickable boxes.
❌  F2.3  The article folder tree supports one level of add / rename /
          delete but not drag-to-reorder or re-parent. There is no manual
          "move to folder" either; folder is only settable from the
          article form's Folder dropdown.
❌  F2.4  Article "Linked" (backlinks) is a placeholder - there is no
          [[mention]] / backlink engine yet, per the design doc's future
          Entry-link table.
❌  F2.5  Only 10 of the ~20 World Anvil-style article categories from the
          reference image have templates. Adding more is a new entry in
          ARTICLE_TEMPLATES, not new code.
❌  F2.6  Linked articles use a loose linked_entity_type /
          linked_entity_id reference with no FK and no cascade-delete.
          Deleting the real NPC/Creature/Spell/Item an article points at
          neither deletes nor unlinks the article - it just becomes a
          dangling reference. Worth deciding on cleanup behaviour if it
          starts to hurt.

--- F3. SHELL, RIGHT PANEL, NAVIGATION -------------------------------

❌  F3.1  The right panel is built but nothing populates it - no page
          wires a row click to a selection + detail view (Faction /
          Quest / NPC / Encounter / Map / Bastion), so it permanently
          shows the empty "select an item" state.
❌  F3.2  Context sidebars are real navigation, but only Encounters'
          actually drives the wrapped section's internal state (its menu
          view, via a lifted prop). Quests' status-group counts and Maps'
          quick-jump list are informational only, not wired as live
          filters into QuestsSection / MapsTable.
❌  F3.3  TopBar's "+New" menu and the command palette's "New quest /
          encounter / map / bastion" actions navigate to the right page
          with a ?new=1 query param but do not auto-open that page's
          create dialog. Each section component would need a small
          autoOpenCreate prop.
❌  F3.4  Widget layout editing is deliberately non-functional - the edit
          pencil is a static placeholder, per the original request's own
          "not a necessity to make it working".
❌  F3.5  The right-panel utility strip's TODO / Notes are per-world
          localStorage scratch state (useQuickToolsStore), not synced to
          any backend or shared across devices. Same reasoning as the
          other prototype-tier features in this codebase.
❌  F3.6  The Docker Hub / GitHub widgets fetch those public APIs directly
          from the browser with no backend proxy. Both degrade to a small
          "unavailable" state on failure, but neither has been tested
          against real CORS / rate-limiting conditions in a deployed
          environment - only local dev.

--- F4. SITUATIONAL TABLES (largely superseded - check before acting) -

⚠️  F4.1  The situational_tables library was global reference content, not
          tied to a campaign / world / "narrative", because there is no
          Narrative entity to join against (Notes' "Narratives" folder is
          prep-note content, not a queryable entity). Tables carried a
          freeform tags array that could have grown real narrative
          linkage later.
⚠️  F4.2  situational_tables had no write endpoints or UI - seeded content
          only, so adding a table meant a new seed-script entry plus a
          re-run.
          NOTE on both: the Part B overhaul replaced this subsystem
          entirely with the new random-tables engine, which does have
          real categories, a normalized tag vocabulary and a full write
          UI. The old backend still exists but is dead (see E5). Treat
          all of F4 as historical unless something is still reading it.

--- F5. RANDOMIZER CONTENT QUALITY -----------------------------------

❌  F5.1  random_professions / random_motivations / random_pitfalls are a
          hand-authored first draft (36 / 5 / 5 entries) seeded once from
          the importer script and never reviewed for tone or setting fit.
          Worth a look before relying on the randomizer in real sessions.
❌  F5.2  The NPC importance randomizer picks among every existing
          importance value except 'monster' (boss / npc / side-character
          / recurring / important / quest-giver / minion / summon), with
          no further narrowing. Flag if that is not the intent.

--- F6. VERIFICATION DEBT (the recurring theme) ----------------------

❌  F6.1  Almost nothing in rounds 4-9 was click-tested in a real browser.
          Verification was type-check + production build + curling the
          running backend, because no browser-automation tool was
          available at the time. Rounds called out as especially worth an
          in-browser pass: the notes/articles round (a new file-explorer
          view and a new filterable table browser), and round 4's Manage
          Tokens popover fix, Reset View auto-rotation, and NPC
          creature-picker autofill.
          Same underlying gap as E12. A Playwright MCP server is now
          configured in .mcp.json, so this is finally actionable.
❌  F6.2  No automated regression test suite anywhere in the project -
          everything has been manual smoke-testing.
❌  F6.3  Touch / mobile input has never been tested for any of the newer
          interactions (drag-and-drop, drawing tools, dice roller),
          despite "works well on both phone and PC" being an original
          product goal (see G1).
❌  F6.4  The ~14 pre-existing MUI v9 typing errors are the same issue as
          E9, and they spread: NotesPage's 3-item sidebar and
          EncountersPage's 3rd sidebar button both copied the existing
          primaryTypographyProps-on-ListItemText pattern verbatim from
          the files they were modelled on. The fix is swapping
          primaryTypographyProps / InputProps / PaperProps for the MUI v9
          slotProps equivalents, before npm run build can be trusted as a
          gate.
