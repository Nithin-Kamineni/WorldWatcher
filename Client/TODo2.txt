D&D DATABASE ARCHITECTURE + 5ETOOLS IMPORT DESIGN
========================================================

Purpose
-------
Build a PostgreSQL database for a D&D campaign-management, encounter-preparation,
map/VTT, and combat application.

Current application entities:
- Monsters / creatures
- NPCs
- Magic items
- Spells
- Maps
- Encounters

Planned entities:
- Factions
- Locations
- Quests
- Campaign/world data
- Combat

Primary structured source:
- 5etools repository, especially its data/ directory.
- Preserve the original 5etools JSON rather than attempting to completely
  normalize it.
- The 5etools data directory currently contains structured areas such as
  bestiary, spells, class, actions, conditionsdiseases, items, races,
  feats, backgrounds, encounters, vehicles, and many other data files.

Architecture principle
----------------------
Use a HYBRID relational + JSONB architecture.

SQL columns:
- Frequently searched
- Frequently filtered
- Frequently sorted
- Frequently joined
- Frequently manipulated by the application
- Important to the combat engine

JSONB:
- Complex structures
- Irregular structures
- Source-specific structures
- Rarely queried structures
- Structures not yet needed by the application
- Future/unknown fields
- Complete original source objects

MOST IMPORTANT RULE:
The importer must be LOSSLESS.

Never discard a 5etools field merely because there is no SQL column for it.
If a field is not modeled relationally, preserve it in raw_data and/or
raw_entities.

Do NOT make the entire PostgreSQL schema identical to 5etools.
Do NOT fully normalize every 5etools field.
Do NOT make the application depend directly on the 5etools JSON format.


DATABASE TABLES
===============

1. sources
---------
Purpose:
Track books, sourcebooks, adventures, SRDs, homebrew sources, and editions.

Columns:
- id: UUID, primary key
- name: TEXT
- abbreviation: TEXT
- edition: TEXT
- source_type: TEXT
- publisher: TEXT
- publication_date: DATE
- page: INTEGER
- license: TEXT
- description: TEXT
- raw_data: JSONB


2. raw_entities
---------------
Purpose:
Lossless storage of every imported 5etools entity, including entities that
the application does not currently model.

Columns:
- id: UUID, primary key
- source: TEXT
- source_file: TEXT
- source_key: TEXT
- entity_type: TEXT
- raw_data: JSONB
- content_hash: TEXT
- imported_at: TIMESTAMP

Rules:
- Never discard unsupported fields.
- Preserve original source identifiers.
- Preserve the complete original object.
- This table is the safety net for future schema changes.


3. creatures
-------------
Purpose:
Main stat-block table for monsters and stat-block-style NPCs.

Columns:
- id: UUID, primary key
- source_id: UUID, foreign key -> sources
- name: TEXT
- slug: TEXT
- edition: TEXT
- creature_type: TEXT
- creature_subtype: TEXT
- size: TEXT
- alignment: TEXT
- challenge_rating: NUMERIC
- proficiency_bonus: INTEGER
- armor_class: INTEGER
- hit_points: INTEGER
- hit_dice: TEXT
- strength: INTEGER
- dexterity: INTEGER
- constitution: INTEGER
- intelligence: INTEGER
- wisdom: INTEGER
- charisma: INTEGER
- description: TEXT
- portrait_asset_id: UUID, foreign key -> assets
- token_asset_id: UUID, foreign key -> assets
- raw_data: JSONB
- created_at: TIMESTAMP
- updated_at: TIMESTAMP

Do NOT store ability modifiers.
Calculate them from ability scores.

Do not initially create relational columns for:
- speed

- skills

- resistances
- immunities
- vulnerabilities

- spellcasting
- variants

RAW_DATA DESIGN
===============

For each major content table, raw_data contains the complete original
5etools object.

For a creature:

SQL fields:
- name
- source
- edition
- creature_type
- size
- alignment
- challenge_rating
- proficiency_bonus
- armor_class
- hit_points
- hit_dice
- strength
- dexterity
- constitution
- intelligence
- wisdom
- charisma

raw_data retains everything else, including:
- speed
- senses
- languages
- skills
- saving throws
- resistances
- immunities
- vulnerabilities
- traits
- spellcasting
- actions
- reactions
- legendary actions
- mythic actions
- variants
- special mechanics
- source-specific fields
- any future 5etools fields

The rule is:
SQL contains the important application-facing projection.
JSONB contains the complete source representation.


ABILITY MODIFIERS
=================

Do NOT store STR/DEX/etc. modifiers as separate columns.

Store:
- strength
- dexterity
- constitution
- intelligence
- wisdom
- charisma

Calculate modifiers from ability scores in application code.

This prevents duplicated and inconsistent data.

PYTHON IMPORTER REQUIREMENTS
============================

Build a Python import pipeline for the 5etools data/ directory.

The importer must be LOSSLESS and IDEMPOTENT.

It must:

1. Recursively scan the configured 5etools data directory.
2. Detect supported entity types.
3. Parse JSON files.
4. Preserve the complete original JSON object.
5. Preserve original source filenames.
6. Preserve original source identifiers.
7. Determine source/book/edition metadata where available.
8. Populate the sources table.
9. Populate creatures.
10. Populate creature_actions where applicable.
11. Populate spells.
12. Populate items.
13. Populate conditions and other supported rules entities.
14. Register imported assets.
15. Extract only explicitly approved important fields into SQL columns.
16. Store the complete original object in raw_data and/or raw_entities.
17. Correctly handle optional fields.
18. Correctly handle arrays and nested objects.
19. Correctly handle 5etools _copy structures.
20. Correctly handle variants and references.
21. Never silently discard unknown fields.
22. Never fail the entire import because one optional field is unfamiliar.
23. Use deterministic source/entity identifiers.
24. Use PostgreSQL upserts so imports can be safely repeated.
25. Calculate content hashes to detect changes.
26. Update existing records when source content changes.
27. Avoid duplicate records.
28. Calculate derived values only when appropriate.
29. Do not store duplicated ability modifiers.
30. Import image metadata and associate images with entities.
31. Keep image bytes outside PostgreSQL.
32. Produce useful logging.
33. Report imported records.
34. Report updated records.
35. Report skipped records.
36. Report malformed records.
37. Report unsupported records.
38. Generate a final import summary.
39. Never modify the original 5etools source files.

Before implementing the importer, inspect the real 5etools data and test
against a diverse set of entities:
- ordinary monster
- dragon
- legendary creature
- mythic creature
- spellcaster
- creature with reactions
- creature with bonus actions
- creature with recharge abilities
- creature with complex resistances
- creature with variants
- creature using _copy
- creature with unusual movement
- creature with multiple attacks
- spells with different area geometries
- complex magic items


IMPORTANT IMPLEMENTATION RULE
=============================

Do not create a giant normalization framework.

The importer should be a thin translation layer:

5etools JSON
    |
    +--> important fields --> SQL columns
    |
    +--> everything else --> raw_data JSONB

The importer is responsible for preserving information, not for inventing
a new interpretation of every D&D rule.


WHAT NOT TO NORMALIZE
=====================

Do not create a relational table merely because a JSON object exists.

Initially keep these in JSONB unless the application needs to query them:
- creature speeds
- senses
- languages
- skill bonuses
- saving throw details
- resistances
- immunities
- vulnerabilities
- complicated traits
- complex spellcasting structures
- unusual monster mechanics
- map walls
- map doors
- map terrain
- map objects
- faction relationships
- faction members
- complex spell effects
- item mechanics
- source-specific structures

Normalize something later when there is a concrete application requirement
such as:
- filtering by it
- sorting by it
- joining by it
- executing it in the combat engine
- displaying/manipulating it frequently

DATABASE DESIGN GOALS
=====================

Priorities, in order:

1. Preserve all source data.
2. Make initial implementation fast.
3. Make common application queries simple.
4. Make combat operations easy.
5. Make map/VTT operations easy.
6. Keep the application independent of 5etools internals.
7. Allow future normalization.
8. Support homebrew/custom content.
9. Allow 5etools data to be re-imported safely.
10. Avoid unnecessary database complexity.


IMPORTANT DISTINCTION: RULES VS COMBAT STATE
============================================

creatures:
"What is a Goblin?"

combatants:
"What is Goblin #3 doing right now?"

The creature table stores the rules/stat block.

The combatant table stores:
- current HP
- initiative
- position
- conditions
- temporary effects
- resources
- action usage
- visibility
- concentration
- current combat state

Never modify the base creature stat block when a combatant takes damage
or receives a condition.

FINAL ENGINEERING PRINCIPLE
============================

The database is NOT a copy of 5etools.

It is:

        5ETOOLS
           |
           v
     LOSSLESS RAW DATA
           |
           v
    APPLICATION PROJECTION
           |
           v
      POSTGRESQL
           |
           v
      D&D APPLICATION

SQL provides structure and usability.

JSONB provides flexibility and complete source preservation.

The schema should evolve based on actual application requirements rather
than attempting to predict every possible D&D rule in advance.
