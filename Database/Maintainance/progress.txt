One real schema bug found and fixed while building this: `sources` had
`UNIQUE(abbreviation, edition)`, but standard SQL NULL semantics mean a
plain unique constraint never catches duplicates when `edition` IS NULL -
which is the common case (5etools doesn't reliably encode "edition" at
the book level). Added a partial unique index
`(abbreviation) WHERE edition IS NULL` alongside the original constraint.

  Bugs found and fixed during this test pass (all three were genuine
  data-shape surprises, not guessed - confirmed against the actual raw
  JSON before fixing):
    1. Recharge abilities: 5etools encodes "(Recharge 5-6)" as a
       {@recharge 5} TAG inside the action name, not literal text. The
       original regex looked for literal text and never matched;
       worse, the generic tag-stripper mangled "Fire Breath {@recharge
       5}" into "Fire Breath 5". Fixed: text.py now renders the
       {@recharge N} tag properly, and creature.py extracts the recharge
       column from the raw tag directly.
    2. Alignment: 5etools has an undocumented shorthand for "alternate
       alignment pairs" on variable-alignment NPCs (e.g. Bandit Captain:
       ["NX","C","G","NY","E"]) that isn't a simple per-code word
       mapping. The naive per-code mapper produced garbage
       ("NX Chaotic Good NY Evil"). Fixed: format_alignment() now only
       produces a display string when every code is a plain recognized
       letter (L/N/C/G/E/U/A); anything else returns NULL for the
       display column rather than a half-translated guess. raw_data
       always has the untouched original regardless.
    3. 2024-revision (XMM/XDMG/XPHB) stat blocks use newer structured
       tags ({@actSave dex}, {@actSaveFail}, {@actSaveSuccess}) in place
       of the old prose phrasing ("Dexterity saving throw"). The old
       save-ability regex only recognized the prose form. Fixed:
       text.py renders the new tags to readable text, and creature.py's
       save_ability extraction now tries the {@actSave} tag first before
       falling back to the old prose-phrase regex.
    4. Minor quality fix: item_type now prefers 5etools' boolean flags
       (staff/rod/wand/wondrous/...) over the raw `type` code field,
       since the raw code (e.g. "M|XPHB") needs the itemType.json lookup
       table to resolve properly (out of scope) and produces a much less
       readable value ("M") than the flag-based label ("Staff") when
       both are present on the same record.

KNOWN LIMITATIONS (documented, not fixed - acceptable given the "thin
translation layer, do not over-engineer" scope of the plan):
  - creature_actions damage extraction only captures the FIRST
    damage/type pair per action text; compound damage clauses (e.g.
    "plus 8d8 fire damage") are not split into separate columns. Full
    text is preserved in description/raw_data regardless.
  - _versions expansion links raw_entities.linked_id to only the FIRST
    expanded creature row when one raw JSON object expands into several
    (rare - only observed on a handful of "variant" monsters). All
    expanded rows are still created correctly; only the raw_entities
    convenience pointer is singular.
  - addSpells/removeSpells/replaceSpells/addSkills _copy mod operators
    are recognized (never crash / never fall back to unsupported) but
    are NOT applied - the base entity's spellcasting/skill block is left
    as-is. This only affects raw_data fidelity for the (rare) monsters
    that both use _copy AND modify spellcasting via that mechanism;
    spellcasting is raw_data-only content regardless (never a column),
    so no relational data is affected.
  - baseitem (mundane gear) and itemGroup are raw-ingested but not
    projected into `items` - matches database_scehma.txt 2.7's own
    "magic items today, mundane items later" scoping.
  - Deliberate malformed-record injection (test-plan item 20) was
    skipped to avoid mutating the read-only 5etools-src checkout;
    per-record SAVEPOINT error isolation was verified by code review
    instead of a live malformed-record test.
  - Stage 5 item-asset matching re-hashes every already-linked item's
    image file on every run (no "skip if already linked" short-circuit
    like creatures have) - correctness is fine (sha256 dedup prevents
    duplicate assets rows/copies), just not maximally efficient on
    repeat runs. Not fixed given time budget; cheap to add later if
    re-import speed on a full unchanged dataset becomes a concern.

  ANSWERING THE ORIGINAL QUESTION ("how long does the script take"):
  On this machine, against a local Postgres instance, a full cold
  import of the entire current 5etools dataset (4,528 monsters, 936
  spells, 2,428 items, ~26k total JSON records across every entity
  type, plus matching/copying ~7,000 images out of the 12GB image
  repo) takes well under a minute (~45 seconds). A subsequent re-run
  with no upstream changes (the normal steady-state case) takes single-
  digit seconds, since almost everything short-circuits on an unchanged
  content hash. This does NOT include the one-time cost of cloning the
  two 5etools repos themselves (5etools-src: ~9s; 5etools-img: several
  minutes, dominated by network transfer of ~12GB - already done once,
  not part of the importer's own runtime).

KNOWN MINOR LIMITATION found during the full run (not fixed, low
priority): a handful of raw-ingest-only entity types that aren't
relationally projected (subclass, subclass_feature, class_feature,
race_feature) showed spurious "updated" counts on the idempotency
re-run despite no source changes. Root cause: a few subclass/feature
entries share the same (name, source) - and therefore the same
source_key - across more than one JSON file, and os.walk's file
traversal order isn't guaranteed stable across runs, so which file's
copy "wins" for that shared key can flip between runs. This never
touches creatures/spells/items/conditions (which showed clean
unchanged counts) and doesn't lose data (raw_entities still holds
whichever version was written), so it was left as documented tech debt
rather than fixed under the current time budget - a real fix would key
raw_entities by (source_file, source_key) more strictly at the
class/subclass level or dedupe upstream before ingest.
